# 墨页 AI-first 扩展路线图

日期：2026-11-10
状态：v2 — 根据外部产品反馈改写（原「功能补齐」路线 → 「AI 辅助写作」路线）

## 背景

墨页 v0.10 已完成 Markdown 编辑、实时预览、图片插入、HTML/PDF 导出、文件夹导入、恢复草稿等核心闭环。原路线图（v1）按「补齐编辑器功能」规划了 22 项功能，但外部反馈指出一个根本问题：**这仍然把墨页理解成传统 Markdown 编辑器，然后不断补齐编辑器应有的功能。**

AI 时代值得重新思考的不是「Markdown 编辑器还缺什么功能」，而是：**当 AI 能够理解文档、操作文档、组织文档，编辑器应该变成什么？**

因此本路线图（v2）将墨页重新定义为：

> **一个以 Markdown 为开放数据基础、以本地文档为工作上下文、由 AI 协助用户思考和创作的写作工作空间。**

## 产品结构：三层架构

```
┌─────────────────────────────────────────────────────┐
│  用户层  Human Writing Interface                     │
│  Markdown 编辑、预览、阅读、选区操作                    │
│  人始终拥有文档的最终控制权                            │
├─────────────────────────────────────────────────────┤
│  智能层  AI Document Assistant                       │
│  理解、分析、生成、修改、组织                          │
│  选区操作 · 文档问答 · 资料检索 · 文档操作              │
│  AI 提议修改，人保留最终控制权                         │
├─────────────────────────────────────────────────────┤
│  数据层  Markdown as Source of Truth                 │
│  本地文件、相对路径、附件、历史版本                     │
│  文档不被锁进专有数据库，随时可用其他编辑器打开          │
└─────────────────────────────────────────────────────┘
```

## 三条产品原则

1. **AI 融入编辑过程**，而不是增加一个独立的聊天产品。
2. **AI 可以操作文档，但不能绕过用户的修改确认**。
3. **用户数据仍归用户所有**，远程模型调用必须明确告知数据范围和去向。

## v0.11：AI 辅助写作（P0，2–3 周）

### 目标

让 AI 参与当前文档的创作过程，形成「选中文字 → AI 理解上下文 → 提出修改 → 用户审阅 → 写入文档」的闭环。

**状态**：已实现（选区操作五动作、当前文档问答、修改提案逐条接受），随 v0.12/v0.13 发布；`v0.11` tag 缺失，记入文末「条目 23」。
**验收标准（补充）**：提案必须逐条接受、复用现有 undo/redo；拒收后原文逐字节不变；API Key 不写入 `session.json` 与 Markdown。以上均已由网页回归与桌面 e2e 覆盖。

### 功能 1：选区 AI 操作

**入口**：选中一段文字后，浮现操作工具栏（或右键菜单）。

**首期五个动作**：

| 能力 | 用户获得的价值 |
|---|---|
| 改写 | 提高表达质量 |
| 精简 | 消除冗余 |
| 扩写 | 将想法发展成完整段落 |
| 解释 | 理解复杂内容 |
| 检查逻辑 | 发现论证漏洞 |

**交互流程**：
1. 用户选中文字
2. 点击动作（如「改写」）
3. AI 返回修改提案（diff 形式，高亮变更）
4. 用户点击「接受」→ 写入文档；点击「拒绝」→ 保留原文
5. 支持「重新生成」获取不同提案

**改动**：
- `web/ai/`（新目录）：选区操作 UI、diff 渲染、提案卡片
- `desktop/ai.cjs`（新）：AI 调用 IPC、Provider 适配
- `web/app.js`：选区监听、工具栏注入

**边界**：
- 仅处理当前选区，不自动修改整篇文档
- AI 提案必须以 diff 形式展示，用户明确接受后才写入
- 无网络时禁用 AI 功能并提示，不阻塞正常编辑

### 功能 2：当前文档问答

**入口**：侧栏「AI」面板或 `Ctrl+Space` 唤起。

**能力**：
- 理解整份文档内容
- 回答用户问题（如「这篇文章的核心论点是什么？」「哪些地方存在逻辑跳跃？」）
- 回答中**定位到原文对应段落**（点击引用跳转）

**交互流程**：
1. 用户打开 AI 面板，输入问题
2. AI 基于当前文档内容回答
3. 回答中的关键引用可点击，跳转到原文位置
4. 支持多轮对话（上下文限于当前文档）

**改动**：
- `web/ai/`：对话面板、引用定位
- `desktop/ai.cjs`：文档上下文构建、问答 IPC

**边界**：
- 上下文范围 = 当前文档（首期）
- 不自动读取其他文档
- 回答中的引用必须能定位到具体段落，不接受无法核验的总结

### 功能 3：安全修改审阅

**入口**：AI 面板中的「AI 修改」模式。

**能力**：
- AI 对整篇文档提出结构化修改建议（非直接覆盖）
- 每条建议包含：位置、原文、建议修改、理由
- 用户可逐条「接受」/「拒绝」/「忽略」
- 支持「全部接受」但需二次确认
- 所有修改可撤销（复用现有 undo/redo）

**改动**：
- `web/ai/`：修改建议列表、逐条审阅 UI
- `desktop/ai.cjs`：文档操作层、批量修改 IPC

**边界**：
- AI 不直接写文件，只生成修改提案
- 用户接受后才写入
- 修改前自动保存快照，支持一键回滚

### v0.11 验收指标

| 指标 | 说明 |
|---|---|
| 接受率 | AI 建议有多少真正进入文档 |
| 撤销率 | AI 修改有多少被用户反悔 |
| 复用率 | 用户是否反复使用 AI 功能 |
| 节省时间 | 完成同类写作任务是否更快 |

**验证方式**：用自己的真实文档和少量目标用户进行一周验证。不统计 AI 调用次数或 Token 消耗。

## v0.12：文档理解（P1，2–3 周）

### 目标

让 AI 理解整份文档的结构与内容，为后续 Agent 能力打基础。

**状态**：功能 4 已实现（`desktop/folders.cjs` 的 `searchFolder` + `web/search.js`）；功能 5 部分实现（`analyzeDocument`/`summarizeDocument`，引用定位已在 AI 面板可用）；功能 6 已实现（`session.json` 的 `recentDocs` + 「文件 → 最近」菜单）。
**验收标准（补充）**：全文搜索需覆盖「导入含 3 个文件的文件夹 → 搜索 → 点击结果 → 文档打开且光标定位」；最近列表需覆盖「打开 A → 打开 B → 最近含 A」。

### 功能 4：全文搜索（跨文件夹）

**问题**：当前查找替换仅限当前文档，忘记标题时无法在文件夹内定位。**全文搜索现在是 AI 获取上下文的基础设施**——没有可靠的检索，知识库 Agent 很容易变成把整个文件夹塞进上下文。

**方案**：新增「文件夹搜索」面板，对已导入文件夹的 Markdown 做纯内存全文扫描（不建索引），支持大小写/正则切换，结果按文件名分组，点击跳转到对应文档与位置。

**改动**：`desktop/folders.cjs`（批量读取 + 匹配）、`web/app.js`（搜索面板 UI）、`desktop/main.cjs`（IPC）。

**边界**：仅搜索已导入文件夹；单次最多 2000 文件；不建持久索引。

**验收**：桌面 e2e 导入含 3 个文件的文件夹 → 搜索关键词 → 点击结果 → 文档打开且光标定位。

### 功能 5：原文定位与文档分析

**能力**：
- AI 回答可定位到原文具体段落（复用全文搜索的读取能力）
- 文档结构分析：自动生成大纲、识别章节层级
- 文档摘要：生成简短摘要，帮助用户快速回忆内容

**改动**：`desktop/ai.cjs`（结构分析）、`web/ai/`（定位 UI）。

**边界**：分析基于当前文档，不跨文档；摘要可手动刷新。

### 功能 6：最近文件列表（原 P0-2，保留）

**方案**：`session.json` 扩展 `recentDocs`（最多 10 条，去重、按时间倒序）。「文件」菜单新增「打开最近 →」子菜单。

**改动**：`desktop/main.cjs`、`web/app.js`。

**验收**：桌面 e2e 打开 A → 打开 B → 菜单「最近」应含 A。

## v0.13：Agent 文档操作（P2，3–4 周）

### 目标

让 AI 理解文档集合，能够跨文档检索、生成、修改和创建文档。这是墨页从「编辑器」走向「写作工作空间」的关键一步。

**状态**：功能 7 部分实现（`desktop/ai.cjs` 已有 `askMultiDocument`，但未经 `preload.cjs` 暴露，界面未接）；功能 8、9 未实现。
**验收标准（补充）**：多文档问答必须由用户显式勾选文档/文件夹，并在发送前显示本次上下文范围；引用可定位到具体文档与段落；生成的文档另存为独立 `.md`，不覆盖原文。

### 功能 7：多文档检索与问答

**能力**：
- 用户指定多个文档或整个文件夹作为 AI 上下文
- AI 跨文档检索相关信息
- 回答中引用具体文档和段落

**改动**：`desktop/ai.cjs`（上下文构建器扩展）、`web/ai/`（多文档选择 UI）。

**边界**：
- 用户必须显式选择文档/文件夹，不默认读取整个硬盘
- 每次向远程模型发送内容时，让用户知道本次发送的上下文范围
- 大文档集合需要截断或摘要，不能无限制塞入上下文

### 功能 8：AI 生成新文档

**能力**：
- 基于当前文档或指定资料，生成新文档草稿
- 用户审阅后决定是否保留、修改或合并

**改动**：`desktop/ai.cjs`（文档创建 IPC）。

**边界**：生成的新文档保存为独立 `.md` 文件，不覆盖原文档。

### 功能 9：AI 整理与结构化

**能力**：
- 将杂乱的记录整理成结构化文档
- 提取关键信息生成知识卡片
- 自动补全缺失的章节结构

**改动**：`desktop/ai.cjs`、`web/ai/`。

**边界**：整理结果作为新文档或修改提案，不直接覆盖原文。

## v0.14+：生态扩展（P3，按需）

### 功能 10：MCP 接口（优先于插件系统）

**背景**：研究 OpenKnowledge 的 MCP 方式——让外部 Agent 使用一组清晰、有限的文档工具（搜索、链接查询、文档创建、修改、删除、历史恢复）。这比先建一个复杂的插件生态更贴近 AI 工作流。

**方案**：提供 MCP 服务器，暴露文档操作工具给外部 AI Agent 调用。

**边界**：工具集有限且明确；需要权限控制；不暴露文件系统全部能力。

### 功能 11：Git 集成

**方案**：检测文档目录是否为 Git 仓库，侧栏显示当前分支/修改状态，支持提交（commit）、查看差异（diff）。

**边界**：仅桌面端；依赖用户已安装 Git；不自动提交。

### 功能 12：插件系统（暂缓）

**背景**：目前尚无证据表明第三方开发者需要为墨页编写插件。先抽象通用插件 API 只会增加维护成本。建议先通过 MCP 验证外部 Agent 的需求，再决定是否开放插件生态。

### 功能 13：CLI

**方案**：提供 `inkstone` 命令行，支持 `inkstone export <file.md> --format html|pdf|docx`、`inkstone watch <file.md>`。

### 功能 14：导出增强（docx / EPUB / 长图）

**方案**：复用导出管线，新增 Word/docx、EPUB、长图格式。

**边界**：仅桌面端；docx 公式转图片；EPUB 按一级标题分章。

### 条目 15：编辑器块级标记显示收窄（P0，立即）

**来源**：用户反馈——光标停在二级标题行时，隐藏的 `##` 会显示成 `## 原样表达，也自由排版`；2026-11-28 已在真实应用复现（`npm run start:web`，Electron 加载同一份 `web/`），期望与 Typora 一致。

**根因（已定位）**：光标进入块后 `web/app.js` 的 `updateActive()`（约 345–351 行）给块加 `.active`，`web/styles.css` 第 1 行 `#editor .active .syntax{display:inline}` 把块内**所有** `.syntax` 从隐藏改为显示。该规则源自 v0.4 富块「激活显示源码」设计（`docs/superpowers/specs/2026-10-24-ink-leaf-v0.4-render-markdown-design.md` 第 151 行），被无差别套到了块级前缀上。悬停不触发，失焦即收回。

**目标**：块级前缀（标题 `#`/闭合 `#`、Setext 下划线、列表、任务、引用、脚注定义）永不因光标显示；行内标记（`**`、`*`、`~~`、`` ` ``、链接、脚注引用）只在光标所在/紧邻的那一处展开；富块（代码/表格/公式/HTML）双态行为不变。

**验收**：标题行任意位置 `.block-marker` 均隐藏且文字无水平位移；行内标记仅紧邻处可见、移入内容中部即收回；`npm run check && npm test` 与 `tests/web/*.py` 全量回归通过；v04/v05 旧口径断言按新语义改写（不删除断言）。

**依赖**：无。

**风险**：可发现性下降，必须与条目 16 同批交付；测试口径变更需在 PR 说明中标注为语义变更。

**阶段归属**：v0.13.x 修补，先于 v0.14。

**实施记录（2026-11-28）**：已完成 A＋B。`web/app.js` 新增 `blockMarker()`（第 53 行，给块级前缀打 `block-marker` 类）与 `revealInlineMarkers()`（第 370 行，只给光标所在/紧邻的行内标记加 `.reveal`），由 `updateActive()` 刷新；`domPoint()`（第 100 行）跳过隐藏标记，避免光标落进标记后被浏览器弹回块首；`Ctrl/⌘+A` 用 `selectAllSelection`（第 38、484 行）记录模型层整篇区间。**隐藏方式最终用「零字号」而不是 `display:none`**：实测 Chromium 原生退格遇到 `display:none` 的内联标记会把「整段标记 + 前一个可见字符」一起删掉（例如 `## 标题` 中间退格得到 `题`），零字号没有该问题；代价是零宽文本仍可被光标进入，由 `skipHiddenMarker()`（第 609 行）把输入挪到标记之后、`hiddenSpanAt()`/`leadingHiddenMarker()`（第 852、869 行）让 Home 与左右方向键跳过标记。**例外**：内容为空的块（刚敲 `## `、列表回车新建项）用 `.pending` 保持前缀可见，否则光标无处可落；有正文后立即隐藏。富块双态未改。测试按新语义改写：v04 的 Setext 断言改为「激活后仍隐藏」并新增「块级前缀常隐、行内标记仅紧邻处展开」用例；v05 的脚注定义断言改为前缀常隐，并新增脚注引用标记紧邻展开用例；`tests/web/inktest.py` 增加 `visible_text()` 以断言「用户看到的文本」（隐藏标记是零宽文本，仍出现在 `innerText` 里）。验证：`npm run check`、246 项单测、12 个网页回归脚本、桌面 e2e 42 项全部通过。

### 条目 16：行首 Backspace 的格式降级（P0，紧随条目 15）

**来源**：同一次排查——标题行首退格实际是删块间空行/吞掉隐藏空格，`##` 最终变成段落里的字面文本（证据：`test-results/heading-probe/report.json` 的 `06_*`、`07_*`，`report2.json` 的 `C_*`）。

**目标**：heading / 列表 / 任务 / 引用在块首退格时删除前缀并降级为正文，走 `apply()` 复用 undo；普通段落行首退格仍合并上一段。

**验收**：四类块各有「行首退格 + 撤销」网页回归用例，`markdown()` 逐字节符合预期；IME 组合输入期间不触发；降级后光标落在原正文开头。

**依赖**：条目 15（标记不可见后，退格是唯一可见的降级入口）。

**风险**：「块首」需同时覆盖原始偏移 0 与可见文字起点；「先降级还是先合并」需要一次明确取舍。

**阶段归属**：v0.13.x 修补，与条目 15 同批。

### 条目 17：双视图原型落地 `web/`（P0）

**来源**：`docs/superpowers/specs/2026-11-28-dual-view-architecture.md` 与 `2026-11-28-dual-view-prototype.md`；原型在 `.superpowers/prototypes/dual-view/index.html`（gitignore，不入库）。

**目标**：按原型落地三态（仅文档 / 并排 / 仅 Agent），覆盖悬浮与固定、Agent 视图左 Agent 右文档、会话历史分组、沉浸文档、多文档五个交互面。

**验收**：三态可显式切换且入口常驻；`<900px` 退化为抽屉并给出提示；提案勾选在文档正文与 Agent 摘要两处同源，无「全部采纳」单按钮；工具轨迹含动作/目标/耗时/结果条数，首字延迟有等待计数，中断后保留已完成步骤；桌面端与 Web 端一致（共用 `web/`）。

**依赖**：条目 24（范围决策）、21（多文档状态）、18（沉浸态与公开接口）。

**阶段归属**：v0.14 视图层。

### 条目 18：严格沉浸态与渲染层公开接口（P1）

**来源**：双视图原型壳目前靠外部 `!important` 覆写 `web/styles.css` 才能得到分栏（例：`.workspace{grid-template-columns:230px minmax(0,1fr)!important}`），说明 `web/` 没有可复用的严格沉浸态与渲染层接口。

**目标**：在 `web/` 内提供正式沉浸态（按需收起侧栏/工具栏、`Esc` 退出），并抽出 3–4 个渲染层入口（挂载文档视图、订阅选区与文档变更、应用外部 patch），不新建第二个编辑器实例。

**验收**：删除原型壳的 `!important` 覆写后仍能正确分栏；接口有最小单测；现有网页回归与桌面 e2e 全绿；`window.inkstone` 只读诊断接口不变。

**依赖**：无（先于条目 17）。

**风险**：接口容易顺手膨胀成重构；与现有 `focus-mode` 语义重叠，应合并而不是新增第二套模式。

**阶段归属**：v0.14 视图层地基。

### 条目 19：并排宽度下的紧凑工具栏（P2）

**来源**：双视图并排时文档栏约 400–500px，工具栏按钮被裁切；现有 `@media(max-width:640px)` 以视口宽度为条件，感知不到分栏宽度。

**目标**：工具栏在容器宽 400–500px 进入紧凑形态（图标化、分组折叠、溢出菜单），不裁切、不出现遮挡按钮的横向滚动；以容器宽度而非视口宽度作断点。

**验收**：1440 / 1180 / 900 / 500 / 400px 五档截图无裁切；Tab 可达全部按钮；≤640px 移动端现有行为不回退。

**依赖**：条目 17。

**风险**：容器查询在 Android WebView 上的支持需确认，否则退回 `ResizeObserver`；紧凑形态会改变按钮顺序，需同步快捷键提示与帮助面板。

**阶段归属**：v0.14 视图层。

### 条目 20：固定态 ≥1180px 宽度门槛重估（P2）

**来源**：原型把固定分栏门槛写成 ≥1180px，该数值来自原型观感，未在真实 `web/` 布局上测量。

**目标**：用真实内容（长标题、表格、代码块、中文正文）测量 1024/1180/1280/1440 下的可读性，给出新的固定态门槛；门槛以下退回「抽屉 + 提示」。

**验收**：一份可复现的测量记录（各宽度下文档栏实际宽度、行宽字符数、工具栏是否裁切），门槛写入条目 17 的实现与样式并有回归截图。

**依赖**：条目 17、19。

**风险**：门槛与条目 19 强耦合，必须一起验收。

**阶段归属**：v0.14 视图层。

### 条目 21：多文档状态隔离（P1）

**来源**：双视图要求「一个 Task 可引用多个 Document」；当前 `web/app.js` 只有一个全局 `history`/`future`/`activeId`/`currentText` 与单个 `STORAGE` 键，切文档即丢撤销栈。

**目标**：草稿按文档分键；每个文档独立撤销/重做栈、`activeId`、AI 上下文；切换文档时保存并恢复光标、滚动位置与选区。

**验收**：A 编辑 → 切 B → 切回 A，历史、光标、滚动完整且 B 的编辑不进入 A 的历史；草稿键在 Web 与桌面两端都能区分文档；AI 面板不串台。

**依赖**：无（可先于条目 17 独立完成）。

**风险**：`session.json` 结构变更需兼容旧版读取，不能静默丢弃草稿；多文档历史栈需要设上限。

**阶段归属**：v0.14 视图层前置。

### 条目 22：会话持久化与文件夹归属（P1）

**来源**：双视图架构指出「Agent Task 是唯一真正缺失的持久化对象」；当前 AI 面板会话在切文档/重启后丢失，且不属于任何文件夹。

**目标**：会话可持久化（标题、时间、所属文件夹、关联文档、步骤与提案状态），支持重命名、删除、跨文件夹检索（复用 `folders.cjs` 索引，不新建扫描）；会话不写入 Markdown，不与 `ai-provider.json` 混存。

**验收**：新建会话 → 关闭应用 → 重开后恢复；重命名与删除实时生效；跨文件夹关键词检索定位到会话与步骤；删除会话不影响文档与草稿。

**依赖**：条目 17、21。

**风险**：工具轨迹容易膨胀，需要上限与清理策略；文件夹重命名/移除后的悬挂引用需要定义。

**阶段归属**：v0.14 视图层。

## AI 架构设计

**核心原则**：不要让 AI 逻辑直接散落在 `web/app.js` 和 `desktop/main.cjs` 里面。建立独立的 AI 能力层。

```
┌─────────────────────────────────────────────────────┐
│  AI Interaction Layer                                │
│  选区操作 · 文档问答 · 任务面板                        │
│  web/ai/  (UI 组件、diff 渲染、对话面板)               │
├─────────────────────────────────────────────────────┤
│  AI Service Layer                                    │
│  ┌─────────────┐ ┌──────────────┐ ┌──────────────┐  │
│  │Provider     │ │Context       │ │Action        │  │
│  │Adapter      │ │Builder       │ │Registry      │  │
│  │(OpenAI-     │ │(上下文范围   │ │(动作注册与   │  │
│  │ compatible) │ │ 控制与告知)  │ │ 权限检查)    │  │
│  └─────────────┘ └──────────────┘ └──────────────┘  │
│  desktop/ai.cjs                                      │
├─────────────────────────────────────────────────────┤
│  Document Operation Layer                            │
│  读取 · 搜索 · 生成修改提案 · 写入 · 撤销              │
│  统一操作接口，支持局部接受/拒绝/回滚                  │
├─────────────────────────────────────────────────────┤
│  Existing Markdown Infrastructure                    │
│  文件系统 · 编辑器状态 · Renderer · IPC               │
└─────────────────────────────────────────────────────┘
```

### 四个关键组件

**1. Provider Adapter**
- 不能把产品绑定到某一家模型服务商
- 至少预留 OpenAI-compatible 接口
- 之后再考虑本地模型（Ollama / llama.cpp）
- API Key 存入系统安全存储（Windows Credential Manager / macOS Keychain），**不写入 `session.json` 或同步的 Markdown 文件**

**2. Context Builder**
- 负责确定 AI 到底能够看到什么
- 上下文范围按顺序扩展：
  1. 当前选区
  2. 当前文档
  3. 用户指定的多个文档
  4. 用户授权的文件夹
- **每次向远程模型发送内容时，让用户知道本次发送的上下文范围**
- 不能因为用户打开了某个文件夹，就默认上传里面所有文档

**3. Document Operation Layer**
- AI 的修改必须经过统一的操作接口
- 不要让模型每次生成整份 Markdown 再覆盖原文件
- 优先产生有明确定位的修改提案
- 支持局部接受、拒绝和回滚
- 权限分离：文件读取、修改、新建、删除是不同权限；**首期不开放删除**

**4. Action Registry**
- 选区动作（改写/精简/扩写/解释/检查逻辑）注册为结构化动作
- 每个动作有明确的输入/输出 schema
- 支持动作级权限检查

### 安全边界

| 风险 | 对策 |
|---|---|
| API Key 泄露 | 存入系统安全存储，不明文写文件；提供密钥管理 UI |
| 文档内容意外上传 | 每次发送前明确告知上下文范围；提供「仅本地模式」开关 |
| AI 误改文档 | 修改提案制，用户逐条确认；修改前自动快照，支持回滚 |
| 上下文注入攻击 | 文档内容作为数据而非指令发送给模型；系统 prompt 与用户内容分离 |
| 第三方 Provider 不可信 | Provider Adapter 可插拔；支持本地模型；发送前可审查 payload |
| 删除权限滥用 | 首期不开放删除；后续开放需二次确认 + 回收站机制 |

## 明确不做（非目标）

- **云同步**：与产品「本地优先」立场冲突；用户可自行用 Git/坚果云等工具同步。
- **自动升级**：当前手动检查更新已足够。
- **图床集成**：默认不集成；如有需求可通过 MCP 或插件实现。
- **完整 WYSIWYG 表格编辑**：当前「点击编辑原文」模式已足够。
- **移动端（Android）多标签**：屏幕空间有限，优先级极低。
- **完整 Agent 平台**：首期不做多 Agent 协作、自动化工作流、全局知识库、复杂 RAG、自动发布。
- **插件系统**：暂缓，先通过 MCP 验证外部需求。

> 本节与 `AGENTS.md`「明确不做」重复时以 `AGENTS.md` 为准；Agent 范围的相关决策见文末「条目 24」。

## 需要验证的核心问题

墨页未来真正要解决的，究竟是「如何让用户更方便地编辑 Markdown」，还是「如何让用户更轻松地把脑海中的想法、零散的材料和复杂的信息，转化成一份高质量的文档」？

本路线图的假设是后者。**Markdown 只是载体，编辑器只是入口，用户真正需要的是完成思考与表达。**

验证方式：
1. 用自己的真实文档进行一周 AI 辅助写作实验
2. 观察接受率、撤销率、复用率
3. 确认用户是否愿意把原本需要自己完成的工作交给墨页
4. 确认用户是否认可最终结果

如果验证失败（用户不用、不认可），则回退到基础功能补齐路线。
