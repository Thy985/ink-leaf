# 墨页双工作视图架构：Document-centric 与 Agent-centric

日期：2026-11-28
状态：草案 v1（基于维护者的产品设计表述整理，待对齐三处冲突后转正式计划）
前序：`2026-11-28-ai-dialog-ux-redesign.md`（v0 假设「对话框唯一主界面」，已被本文件取代其前提）

## 一、本次修正了什么

v0 方案的隐含假设是：**无论什么任务，都以对话框为主交互界面**。因此 v0 的所有减法都在优化这个前提——砍 tab、收拢入口、统一结果形态。

这个前提不成立。对 AI-Markdown 应用，至少有两种工作重心，其**一级对象**不同：

| | Document-centric | Agent-centric |
| --- | --- | --- |
| 核心对象 | 文件 | 任务 |
| 页面主体 | 编辑器 | Agent 工作区 |
| 用户意图 | 修改内容 | 完成目标 |
| 上下文 | 当前文档、选区 | 多文档、文件夹、外部资源 |
| AI 行为 | 局部辅助 | 多步骤执行 |
| 交付结果 | 文档内修改 | 一个或多个成果 |
| 人的角色 | 作者 | 任务负责人、审查者 |

**结论：采用双工作视图，而不是让一种模式覆盖所有场景。** v1 保留 v0 中仍然成立的部分（统一变更块、上下文 chip、删除分析 tab 与 trace 常驻），但**不再把对话框当作唯一入口**。

## 二、产品定位

> **Human + Agent × Documents**
> 人和 Agent 围绕持久化文档资产协作。

- **Document-centric**：以人为主导，AI 辅助创作与修改
- **Agent-centric**：以目标为主导，Agent 执行复杂文档任务
- **Shared Infrastructure**：文件、上下文、权限、变更、历史与撤销共享

关键关系：**Document 是持久化资产，Agent Task 是围绕目标展开的工作过程**。一个 Task 可引用多个 Document，也可产生新 Document；一个 Document 可被多个 Task 使用。二者不是一对一。

## 三、必须共享的底层（不做两套 AI 模块）

```
Workspace（统一的文件、权限、上下文环境）
├─ Document View   文档编辑 · 选区操作 · 局部提案
└─ Agent View      任务管理 · 多步骤执行 · 成果审查
        ↓ 共享
Document Service   文档读写、Patch、Diff、版本
Agent Runtime      任务、上下文、工具、执行
Proposal Engine    提案、审批、事务、撤销
Context Service    文件选择、检索、权限
```

**墨页现有的 H0–H2 恰好已经是这个形状**（这是本次盘点最重要的好消息）：

| 提议中的组件 | 仓库现状 | 结论 |
| --- | --- | --- |
| Agent Runtime | `desktop/ai/harness.mjs`（SDK 工具循环 + trace + 步数上限） | ✅ 已具备 |
| Context Service | `desktop/ai/{tools,workspace}.mjs` + `folders.cjs`（只读工具、内存索引、范围声明） | ✅ 已具备 |
| Proposal Engine | `desktop/ai.cjs` 的 `createProposal` / `diffText` + 渲染层 accept/reject + 复用 undo | ✅ 已具备，但**形态分散**（见 v0 第七节） |
| Document Service | `desktop/files.cjs`（原子写、BOM/CRLF、冲突检测） | ✅ 已具备 |
| Agent Task | ❌ 不存在 | **唯一真正缺失的一块** |
| Workspace 实体 | ⚠️ 目前 = 已导入文件夹的集合（H2） | 需确认是否升级为一级对象 |

也就是说：**双视图不需要重写 AI 层**，缺的是「任务」这个持久化对象，以及两个视图层的组织方式。

## 四、三处必须先对齐的冲突

这三条不解决，方案落地会与仓库既有约束打架。

### 冲突 1：AGENTS.md 把「完整 Agent 平台」列为非目标

`AGENTS.md` 的非目标原文：

> 完整 Agent 平台/多 Agent 协作……遇到相关需求先与用户确认，不要自行扩大范围。

而 Agent-centric 需要 `Agent Task` 作为一级对象。这不必然等于「Agent 平台」，但边界必须写清楚，否则：

- 未来 Agent 会拿「双视图」当理由不断扩张（多 Agent、自动编排、后台常驻任务……）
- 维护者的「人工检查四处」会失效，因为新增的能力面没有边界

**建议的最小边界**（供讨论）：

| 做 | 不做（维持非目标） |
| --- | --- |
| 用户发起、可中断、可回滚的**单任务** | 多 Agent 协作、任务间自动编排 |
| 任务状态持久化（可恢复） | 后台常驻/定时自动执行 |
| 成果写入用户文件系统 | 云端任务队列 |
| 复用现有只读工具 + 提案制 | 让 Agent 直接写盘、跳过人确认 |

若接受这个边界，需要**明确修订 AGENTS.md 的非目标表述**，而不是让代码先跑在规则之外。

### 冲突 2：「Workspace」一词已被占用，且语义不同

- 你方案中的 Workspace = 文件、资源、权限、上下文的工作范围（**一级对象**）
- H2 已实现的「工作区」= 已导入文件夹的**归组**（侧栏一个面板，只读索引）

两者同名不同义，直接沿用会让后续维护者混淆。**建议**：

- 你的 Workspace 概念保留，但实现上暂不新建实体，先复用 H2 的文件夹集合作为其最小实现
- UI 上 H2 那个面板改名为「链接」或并入文档视图，避免与一级对象「工作区」撞名
- 若要真正升级为一级对象，单独立项（涉及权限模型、跨文件夹上下文边界）

### 冲突 3：任务持久化与「本地优先」的落点

Agent Task 需要持久化（可恢复、有历史成果）。按 `AGENTS.md`：

- API Key 存 `ai-provider.json`，**不得写入 session.json**
- 文档内容不上传服务器
- 现有 `session.json` 只存路径，不存内容（`{ version, folders, activeFolder, lastDoc, recentDocs }`）

**建议**：Task 存独立文件（如 `userData/tasks.json`），只存**任务描述、涉及文档路径、状态、成果路径**，**不存文档正文**；任务执行时的中间上下文只在内存。这样与既有约束一致。

## 五、分阶段实施

按你的优先级，并映射到仓库现状：

### 第一阶段：Document-centric 做扎实

| 项 | 说明 | 依据 |
| --- | --- | --- |
| 统一变更块 | 选区改写 / 审阅 / 问答的修改结果收敛为一种「diff + 应用/换一个/忽略」 | v0 4.3 |
| 上下文 chip | `@` 显式选上下文，取代被动提示条 | v0 4.1，调研结论 |
| 删除分析 tab | 结构与统计本可本地算，不需占一个 AI tab | v0 4.5 |
| trace 常驻 → 按需展开 | 执行过程默认隐身，出错才展开 | v0 4.2 |
| 审阅并入变更块 | 删除「修改审阅」tab，动作走 `/` | v0 4.3 |

**预期**：`web/ai.js` 788 → 450–550 行；AI 面板 tab 3 → 0；「采纳修改」入口 3 → 1。

### 第二阶段：轻量 Agent View

只做**能被验证**的最小闭环，不建编排平台：

- 任务输入：一个目标描述 + 用户显式选的上下文范围（文件夹/多篇文档）
- 执行：复用 `runAgent`（工具循环 + trace + 步数上限）
- 状态：进行中 / 已完成 / 失败 / 已取消（可中断）
- 成果：产出的 `.md` 写入用户文件系统（**新文件，不覆盖原文**）
- 审查：变更块逐条确认（复用第一阶段）
- 视图切换：文档视图里「交给 Agent 处理」→ 升级；Agent 视图里点成果 → 回到文档视图
- **切换不丢上下文**（同一会话，不新建）

### 第三阶段：Task 成为持久化对象

- 任务恢复、历史成果
- 与 MCP 衔接（外部 Agent 复用同一工具注册表——`desktop/ai/tools.mjs` 已为此预留）
- 仍不做多 Agent 协作

## 六、视图切换的设计原则

不建议只在顶部加两个 Tab 让用户自选。按任务性质推荐，但保留人工控制：

| 用户行为 | 推荐 |
| --- | --- |
| 打开 `.md` / 选区改写 / 当前文档问答 / 审阅全文 | Document |
| 根据文件夹整理文档 / 多文档研究综合 / 创建一组关联文档 / 长时间任务 | Agent |

三个入口：

1. 显式切换按钮（随时）
2. 「交给 Agent 处理」：文档 → Agent，用于从简单任务升级
3. 「打开相关文档」：Agent → 文档，点成果直接定位

**硬约束**：切换视图不创建新会话、不丢上下文。典型流程——文档模式下说「帮我根据实验记录整理总结」，系统识别涉及多篇 → 提示「是否在 Agent 工作区执行？」→ 确认后进入，原任务与上下文保留。

## 八、我的补充意见（供参考，非必须采纳）

**一个可能被低估的风险**：Agent View 的价值主张是「用户不知道要改哪些文件」，这意味着**上下文选择必须由 Agent 检索决定**。而当前 `search_folder` 的返回是「最多 12 条片段」，对「整理整个知识库」这类任务远远不够。

所以第二阶段之前，**上下文服务需要一次实质增强**（分页/迭代检索/按文档聚合），否则 Agent View 会退化成「用一个更大的对话框做和文档视图一样的事」——正是你方案里警告的那个失败模式。

建议把「Context Service 增强」列为第二阶段的前置项，而非并行项。
