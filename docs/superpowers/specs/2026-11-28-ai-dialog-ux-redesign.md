# AI 前端体验诊断与对话框重构方案

日期：2026-11-28
状态：草案（待维护者确认方向）
触发：维护者提出「应该做减法，AI 部分在前端暴露给用户有什么？用户体验会好吗」，并指出**对话框才是核心**——如何在对话框里把信息与上下文方便地交给 Agent、Agent 如何执行任务、如何交付结果。

## 一、现状盘点（实测）

| 维度 | 当前 |
| --- | --- |
| `web/ai.js` | **788 行** |
| AI 相关 CSS 选择器 | **106 条** |
| 入口 | 菜单「AI」7 项、选区浮层 5 个动作、侧栏「工作区」tab |
| AI 面板 | 3 个 tab：问答 / 修改审阅 / 分析 |
| 侧栏面板 | 3 个 tab：文档大纲 / 文件夹 / 工作区 |
| 设置 | 4 个字段（名称、地址、模型、API Key） |

**用户要面对 6 个 tab、2 个面板、17 个交互入口**，而核心价值只有一件事：让 AI 把文字改好。

## 二、诊断：对话框被做成了一个「功能抽屉」

当前对话框（`data-page="chat"`）本身只有一个输入框、一个发送按钮、一个自述式的上下文提示。**真正的能力都不在里面**：

- 「修改审阅」是另一个 tab，用户得先切过去、再描述要求
- 「分析」是第三个 tab，两个按钮
- 选区改写又不在面板里，是浮层

也就是说：**同一个意图（「帮我改这段」）散落在三个地方**，用户在学会这套界面之前，不知道从哪下手。

### 更根本的问题

我把「上下文从哪来」「AI 做了什么」「结果怎么交付」这三件事，做成了**用户需要理解的概念**，而不是**界面自然承载的动作**：

| 这三件事 | 我的做法 | 问题 |
| --- | --- | --- |
| 上下文从哪来 | 自动整篇/检索 + 一行提示「整篇发送」/「按需检索」 | 用户无权决定，只能被告知；且提示是技术承诺，不是操作 |
| Agent 怎么执行 | trace 折叠块「检索了 2 步（1 步未能完成）」 | 用户不关心 AI 查了几次，只关心结果对不对 |
| 结果怎么交付 | 提案卡 / 审阅卡 / 纯文本回答 —— **三种形态** | 同一个「采纳修改」动作有三种入口与三种确认方式 |

## 三、调研：成熟产品怎么解这道题

### Cursor Agent（编程，但交互模型最成熟）

对话框里只有两个交互原语：

- **`@` 提上下文**：`@文件`、`@文件夹`、`@终端`、`@历史对话`、`@Git 差异`、`@浏览器`。**用户显式指定**要看什么。
- **`/` 提能力**：调用 skill/模式，一次性附加到这条消息，或「作为模式」常驻。

关键设计判断（其文档原话意译）：

> 当你明确知道哪些文件相关时才用 `@`；**如果不确定，就别用——Agent 会自己搜索找到相关文件**。

也就是说：**显式指定与自动检索是并列的两条路，由用户按把握程度选，而不是系统替他决定后告知**。

另外两点值得借鉴：

- **上下文用量环**：输入框旁边一个环显示窗口占用，点开按类别（系统提示/工具/规则/历史）拆分。**这是把「发送了多少」变成可操作的可视化，而不是一行文字提示。**
- **检查点（Checkpoint）**：每次大改前自动快照，在时间线里点任意检查点预览并回滚。**交付结果时，回滚是默认能力而不是附加功能。**

### 对照结论

| 能力 | Cursor | 墨页当前 |
| --- | --- | --- |
| 显式喂上下文 | `@` 提文件/文件夹/历史 | ❌ 无，只能整篇或自动检索 |
| 能力挑选 | `/` 提 skill | ❌ 无，能力分散在 tab |
| 用量可视化 | 环 + 分类明细 | ❌ 一行文字 |
| 可回滚 | 检查点时间线 | 部分（undo，但无检查点） |
| 结果审阅 | 统一为 diff + 逐个处理 | ⚠️ 三种形态并存 |

## 四、方案：把对话框做成唯一的执行界面

### 核心原则

> **一个输入框，承担全部三种交互：提问、给上下文、下指令。**
> 其余 UI 只在需要时出现，且不占用常驻空间。

### 4.1 对话框的输入模型（借鉴 `@` 与 `/`）

输入框内支持两个前缀触发器：

| 触发器 | 作用 | 对应「三件事」 |
| --- | --- | --- |
| `@` | 选取上下文：当前文档、某个已导入文件夹、某篇文档、上次对话 | **信息与上下文怎么给** |
| `/` | 选取动作：改写 / 精简 / 扩写 / 解释 / 检查逻辑 / 审阅全文 | **Agent 执行什么任务** |

- 都不用时：就是普通提问，Agent 自己决定检索
- 用 `@` 时：明确告诉 Agent 看哪里，并**在输入框内以 chip 形式显示已选范围**（可删除）
- 用 `/` 时:把一个预置动作模板填进输入框，用户可再补充要求

**这解决了「上下文提示」的问题**：不再需要一行「整篇发送」的被动告知，而是用户主动选了什么就显示什么 chip。没选时提示「将自动检索」——比现在的双分支文案简单。

### 4.2 Agent 执行过程：默认隐身，可按需展开

- 执行中：输入框位置变成一行状态（「正在检索 2 篇文档…」），**不新增面板**
- 完成后：结果下方一个极小的「详情」链接，点开才看 trace
- 失败/被拒：**才**主动展开并说明原因

**删除**：常驻的 `details` 折叠块、常驻的上下文提示条。

### 4.3 结果交付：统一为一种形态

不论来源是选区改写、审阅还是问答，**修改类结果统一为「变更块」**：

```
┌─────────────────────────────┐
│ 改写 · 第 3 段              │
│ - 原句……                    │
│ + 新句……                    │
│ [应用]  [换一个]  [忽略]     │
└─────────────────────────────┘
```

- 一处「应用」，复用现有 undo
- 「换一个」＝重新生成
- 多条时顶部出现「全部应用」，二次确认

**问答类结果**（纯信息、不改文档）保持为普通消息，不套变更块。

这样**删除「修改审阅」tab**——它和选区改写本来就是一件事。

### 4.4 能力收拢

| 保留 | 移除 / 降级 |
| --- | --- |
| 对话框（唯一入口） | ~~修改审阅 tab~~（并入变更块） |
| `/` 预置动作（5 个选区动作 + 审阅全文） | ~~分析 tab~~（结构统计本可本地算，不需要模型） |
| 选区浮层（保留，作为快捷方式） | ~~trace 常驻折叠块~~（改为按需展开） |
| 设置面板 | ~~上下文范围提示条~~（改为 chip） |
| | 侧栏「工作区」tab → 降为菜单项，默认不显示 |

### 4.5 关于「分析」tab 的处理建议

「分析文档结构」是**纯本地计算**（`analyzeDocument` 我们已经有，不调模型），不该占一个 AI tab。建议：

- 大纲已有（左侧栏「文档大纲」）
- 统计（字数/段落/代码块）放到文档信息，随文档实时更新
- 「AI 摘要」价值存疑，建议删除或并入 `/` 动作

| AI 面板 tab | 3 | 0（单一对话框） |
| 侧栏 tab | 3 | 2（去掉工作区） |

## 六、实施建议（分步，每步可独立验证）

| 步骤 | 内容 | 风险 |
| --- | --- | --- |
| **1** | 移除「分析」tab；统计改本地计算 | 低（删除为主） |
| **2** | 审阅并入选区动作，统一为变更块 | 中（涉及提案卡与审阅卡合并） |
| **3** | 删 trace 常驻与上下文提示条 | 低 |
| **4** | 引入 `@` 与 `/` 输入触发器 | 中（新增交互） |
| **5** | 工作区 tab 降级为菜单项 | 低 |

建议 1、3、5 先做（纯减法，立刻见效），再评估 2 与 4。

## 七、需要维护者拍板的点

1. **`@` 与 `/` 是否要做？** 这是对话框能力的实质增强，也是本方案的核心；如果不做，本方案退化为「只删不加」。
2. **审阅并入变更块**：会改变现有审阅交互（现在是一个 tab + 逐条卡片），需确认可接受。
3. **工作区功能**：降为菜单项，还是直接移除？它是我按路线图做的，尚未验证真实需求。
4. **AI 摘要**：保留、并入 `/` 动作，还是删除？

## 八、与 AGENTS.md 的一致性

- 未改动任何安全边界（上下文仍由用户显式或用户已导入范围决定）
- 「AI 只产出提案、人保留最终控制权」不变，只是把三种确认形态收敛为一种
- 符合「最小改动」：本方案以**删除**为主，新增仅 `@`/`/` 两个触发器
